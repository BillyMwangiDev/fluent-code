## 1. First 5 minutes — step by step

1. **Splash** (`splash-first-run.png`) — mark, wordmark, "starting local engine…", then provider
   badges and "press enter to continue." This is a hard-gated screen: `renderSplash` polls the
   daemon up to 25×100ms, then fetches providers/credentials, with an extra 800ms retry if no CLI
   shows as installed yet (`app/src/pages/splash.ts:9-44`). For a warm daemon this is ~1s; worst
   case ~3.5s. The screen adds a deliberate "press enter" gate on top with no setup value — a
   returning user pays this cost every launch.
2. **Branch point most audits will miss**: `advance()` sends the user to `orchestration` if
   `prefs.workspacePath` is set, or any credential chain has accounts, or any provider CLI is
   already installed — **otherwise** to `onboarding` (`splash.ts:66-71`). Realistically, most people
   trying an agent-orchestration tool already have Claude Code or Codex installed. That means the
   rich onboarding screen (`onboarding.png`, from source — see §3 caveat) — 7 provider cards
   explaining CLI login vs. API key vs. OpenRouter — **is skipped by the majority of real first
   users**. It is also the *only* place credential setup is explained in prose; nothing on the
   empty-state or launch sheet mentions it. Most users will never see this screen at all.
3. **Landing screen for the common case: the orchestration empty state** (`empty.png`). This is
   good design — the launch form is embedded directly as the empty state rather than a separate
   "welcome" page (`app/src/workspace.ts:411-442`), matching how Linear/Raycast fold onboarding
   into the real UI instead of a wizard.
4. User must type or browse a working directory (no default, no recent-folders list beyond the
   rail's project switcher once lanes exist), pick "main agent + subagents" or "same brief to
   every lane" (defaults to orchestrate), optionally type a brief, and click start. The per-provider
   stepper rows are dense and good: they show install/connect state inline instead of failing
   silently (`app/src/launch.ts:163-201`).
5. Session(s) launch as the **real CLI process** in a terminal tile; first visible value is the
   first streamed token from that CLI. This part is entirely gated by the CLI's own cold start +
   auth handshake, which Fluent correctly never wraps or fakes (per the one rule in
   `CLAUDE.md`).

**Time-to-first-value estimate**
- **CLI already installed & logged in** (the realistic case for this audience): ~30–60 seconds —
  splash (~2s) + pick directory (~10s) + optional brief (~5s) + CLI cold start (~5–15s).
- **Nothing installed** (true cold machine): several minutes, gated by the CLI vendor's own
  install + OAuth flow, which Fluent correctly defers to rather than reimplementing. This is
  architecturally correct per the spec's one rule, but it means the product's *own* first-run
  polish (steps 1–4) is not what determines time-to-value for a genuinely new user — the CLI
  vendor's onboarding is on the critical path and Fluent does nothing to shorten it beyond a
  one-click "install" link.

**Where a first-time user gets bored/lost**
- The splash "press enter" gate (no information, no shortcut to skip it on repeat visits).
- The product's two headline differentiators — **credential fallback chains** and **cross-agent
  coordination** — are invisible during onboarding and the launch flow. Credentials are one rail
  click away but nothing points there; coordination only becomes visible once a lane exists *and*
  the sidebar happens to be open *and* the agent has actually populated the task board via the
  `fluent-coord` CLI (which won't happen in a plain single-lane run unless the agent is briefed to
  use it). A user could run Fluent for weeks as "a nicer multi-terminal" and never discover either
  feature. See finding P1-1 below.

## 2. Per-screen findings (severity: P0 blocks value, P1 hurts daily use, P2 polish)

### Splash (`splash-first-run.png`)
- P2: unskippable "press enter" step on every launch, even for a returning user with an active
  workspace. Best-in-class (Warp, Zed) either skip this entirely on warm start or make it instant
  (auto-advance after a timeout) rather than input-gated.

### Onboarding (`app/src/pages/onboarding.ts`, no clean screenshot — see caveat below)
- **P1: orphaned screen.** `grep`-verified: `{name: 'onboarding'}` is only ever navigated to from
  `splash.ts:71`. No rail item, no link from Credentials, no "add another provider" affordance
  anywhere else in the app (`app/src/router.ts`, `app/src/shell.ts` — confirmed no other
  `navigate({name: 'onboarding'})` call exists). Once a user has one CLI installed, this screen —
  and its explanation of API keys, OpenRouter, and the model-linked OpenCode providers (Qwen/GLM/
  NVIDIA) — becomes permanently unreachable through the UI. The only way back is Credentials
  (which covers per-provider chain management but not the "here's how each provider type works"
  framing) or Catalog. **Caveat**: I could not get a real screenshot of this screen — the QA
  fixture (`scripts/ui-qa-harness.html`) always reports Claude Code and Codex as
  `installed: true` in `providers.list`, so `canStart` is always true and the harness's own
  `onboarding` scenario in `shoot.mjs` never actually reaches this route (its `onboarding.png`
  output is just the ordinary workspace). I verified this by reading `splash.ts`'s `canStart`
  logic and by attempting to monkey-patch the fixture's provider list at runtime (see
  `onboarding-real-fail.png` — the patch raced the harness's own script and produced a load error,
  not worth further engineering time for a QA-script fixture gap). This finding is based on
  direct source reading of `app/src/pages/onboarding.ts`, not a screenshot.

### Orchestration workspace / lane grid
- `workspace-1.png`, `workspace-3.png`, `workspace-6.png`, `workspace-10.png`, `workspace-12.png`,
  `workspace-12-nosidebar.png`, `rows-12.png`, `focus-6.png`, `empty.png`
- **Good**: grid/rows/focus layout modes, ⌘1–9 lane jump, the composer's focused/checked/all
  targeting, the auto-promoted main-agent-first ordering (`workspace.ts:37-52`). This is the
  strongest screen in the product.
- **P1: density collapse past ~6 lanes.** At 9–12 lanes (`workspace-10.png`, `workspace-12.png`)
  the grid drops to a 3-column layout where lane titles truncate mid-word ("Refact…", "Op…",
  "Mi…", "Wr…") and the terminal pane shows perhaps 4–6 lines of text at ~10px. `maxLanesPerProvider`
  is 10 per provider (`app/src/launch-plan.ts:47`) — across 6 providers the launch sheet lets a
  user request up to 60 lanes, but the grid is unreadable well before that. AGENTS.md's own
  designed-screens list describes "five simultaneous terminal lanes" (item 6) — the shipped grid
  degrades badly beyond that number, with no intermediate density option (e.g., a compact
  "activity only" row for lanes not currently being watched).
- **P1: topbar/rail can contradict the workspace's own project header.** `workspace.ts:57` derives
  the active project via `currentProject(prefs.workspacePath, store.sessions)`
  (`app/src/project-scope.ts:17-26`), which correctly falls back to the most-recently-active
  session's project when no workspace pref is set. But `renderTopbar()`
  (`app/src/shell.ts:38-49`) and the rail's workspace switcher (`shell.ts:60-90`) both read
  `prefs.workspacePath` **directly**, with no fallback. Result: in any scenario where fluentd
  already has live lanes but the client's local `workspacePath` pref is unset (fresh install
  reconnecting to a running daemon, cleared app data, new machine profile against a remote
  daemon), the workspace strip correctly says "fluent-code · 5 running" while the topbar says "no
  workspace selected" and the rail says "choose a workspace" — three contradictory statements
  about the same fact on one screen. Confirmed via source; the QA fixture reproduces it in every
  screenshot in this audit (top-left corner text "no workspace selected" is visible in nearly
  every screenshot listed here, including ones where the strip shows a running project).
- **P1 (real bug, verified, not visual guesswork): terminal panes ignore light appearance mode.**
  I switched to light mode (`light.png`, then re-verified with `light-recheck.png` /
  `light-final.png` / pixel crops `rail-corner-crop.png` and `lane-crop.png`). Verified via
  `getComputedStyle` in-page: `document.documentElement.dataset.theme === 'light'`, rail/topbar
  background correctly resolves to `rgb(250, 249, 245)` (confirmed both by computed style and a
  cropped screenshot of the rail corner — genuinely light). But the lane terminal panes stay
  rendered dark (confirmed by a direct pixel crop, `lane-crop.png` — dark background, light text).
  I went further and reconstructed `terminalTheme()`'s exact output at runtime
  (`app/src/terminal.ts:6-29`): every field resolves correctly (`background: "#fbfaf6"`,
  `foreground: "#1f1e1d"`, etc. — genuinely the light palette). So the CSS tokens and the JS that
  reads them are both correct; the defect is downstream, in how xterm.js's DOM renderer
  (`xterm-dom-renderer-owner-1`, confirmed in the fixture — not the canvas renderer) applies or
  caches that theme object when the tile is (re)attached under light mode. This is worth a
  focused look at `attachLaneTerminal` in `app/src/terminal.ts:63-90` — likely a timing issue
  where the terminal is constructed before the DOM renderer's own stylesheet/color cache is primed,
  or a caching bug where the DOM renderer needs `terminal.options.theme = {...}` reassigned rather
  than passed only at construction. In dark mode this is invisible because xterm's built-in
  default (near-black) happens to look plausible; in light mode it reads as a broken feature.

### Launch sheet / new-session form (`sheet.png`, `sheet-parallel.png`, `new-session.png`)
- **Good**: one shared component (`launchForm` in `app/src/launch.ts:136-324`) powers the empty
  state, the `+ agents` sheet, and the New Session page — genuinely consistent, and the
  mode-switch copy ("You brief one agent. It splits the work…" vs. "Every lane gets the same
  brief…") is some of the clearest microcopy in the app.
- P2: in the sheet variant, provider detail text (e.g., "via OpenCode · qwen3-coder · Model Studio
  work") clips against the sheet's fixed width with no tooltip/title fallback visible in the
  screenshot.

### Sessions / Session detail (`sessions.png`, `session.png`)
- Clean, dense table; archive/delete-all-archived affordances up front. No major issues found.

### Usage observatory (`usage.png`)
- P2: the "provider usage" table (bottom of the page) has no column header row — values like
  "cache —" / "cost —" appear directly under a bold model name with no labels, which works once
  you've seen the (separate, labeled) `spend` page but is not self-explanatory on first view.

### Spend (`spend.png`)
- Good density: total, daily trend chart, totals grid, per-model breakdown with a model/day
  toggle. No issues beyond fixture data only spanning 5 days under a "30d" toggle (a fixture
  artifact, not necessarily a product bug — worth a real-data check).

### Credentials (`credentials.png`)
- This is the best-built expression of a stated differentiator in the app: numbered fallback
  chain, "not connected" state with the exact CLI command to fix it, a separate "manual only"
  section for accounts intentionally excluded from auto-fallback, and a clear three-way
  when-a-credential-hits-its-limit control. The core problem is discoverability (see P1-1 above),
  not this screen's own design.

### Catalog (`catalog.png`)
- Good: explicit provider-owned vs. third-party trust badges, source policy control up front.

### Design workspace (`design.png`) / Preview & visual check (`preview.png`)
- **P0-ish gap between the documented vision and the shipped screen.** AGENTS.md's designed-screens
  list (items 7–8) describes Preview as "docked localhost preview, DOM/source mapping, console and
  network state, visual comparison, mismatch-to-agent actions, and approval/task actions," and
  Design as "component/token specs, live preview, source mappings... design-to-build handoff."
  The shipped `preview.ts` is 97 lines: a URL field, an "open preview" button that launches a
  separate guarded native window, and a recipe-approval note. None of DOM/source mapping,
  console/network state, or visual comparison exist in-page — that entire promised surface is
  deferred to a window this audit (and a real user) cannot inspect from inside Fluent itself. The
  Design page is similarly a connector-status shell (OpenDesign reachability, Pen CLI status,
  three plain-text task fields) rather than the described component/token/live-preview workspace.
  This may reflect legitimate phased build-out, but as shipped it under-delivers relative to what
  the product explicitly claims to differentiate on, and a new user reading AGENTS.md before
  trying the app will be disappointed by what's actually there.

### Source control (`source-control.png`)
- Clean and appropriately minimal for what it shows (current branch/PR, assigned issues, open
  PRs). No issues.

### Remote (`remote.png`)
- Clear form, sensible default copy about SSH-only tunneling. No issues.

### Themes (`themes.png`)
- Good layout (appearance mode segmented control filtering a bundle gallery, live terminal
  preview swatch). See the light-mode terminal bug above — it undermines confidence in this page's
  own promise.

### Palette / shortcuts (`palette.png`, `palette-commands.png`, `shortcuts.png`)
- Excellent. Fuzzy match across navigation, running lanes, and page-specific commands in one
  place; the shortcuts sheet is complete and matches what's actually wired in `workspace.ts` and
  `shell.ts`. This is genuinely best-in-class (on par with Raycast/Linear's command palettes).

### Rail (`rail-collapsed.png`, `rail-collapsed-page.png`, `sidebar-setup.png`, `ticket-menu.png`)
- Collapse-to-icons is clean and remembers state. The live-lanes list under the nav groups (with
  attention dots, lead/subagent icons) is a strong piece of ambient awareness other tools in this
  category don't have.
- P2: at a narrow/short viewport (`narrow.png`, 1180×760) the rail's nav groups can scroll past the
  visible area with no visible scroll-shadow/affordance hinting more items exist below "themes" —
  `overflow: hidden auto` is present (`app/styles.css:317`) so it's not actually broken, just easy
  to miss that it's scrollable.

### Narrow window (`narrow.png`, `narrow-1024-lane1.png`)
- Holds up reasonably well down to 1180×760 and even 1024×700 for a single lane — text wraps,
  sidebar stays usable. No breakage found.

## 3. Ten highest-impact changes, ordered by impact/effort

1. **Fix the light-mode terminal rendering bug.** `app/src/terminal.ts` — `attachLaneTerminal`
   (~line 63) constructs `new Terminal({theme: terminalTheme(), ...})` once; investigate whether
   the DOM renderer needs `terminal.options.theme` reassigned after `terminal.open()`, or whether
   tiles created before a theme switch need re-instantiation. High impact (visibly broken feature,
   screenshot-provable), likely low effort once the renderer behavior is understood.
2. **Make the topbar/rail workspace label agree with the workspace strip.** In
   `app/src/shell.ts`, `renderTopbar()` (~line 42) and `renderRail()`'s switcher (~line 70) should
   use the same `currentProject(prefs.workspacePath, store.sessions)` fallback that
   `workspace.ts:57` already uses, instead of reading `prefs.workspacePath` raw. Small, contained
   fix; removes a genuinely confusing self-contradiction visible on screen.
3. **Surface credential fallback and coordination during/after first launch, not just in
   onboarding.** Add a one-line nudge in the empty-state (`workspace.ts` `renderEmptyState`,
   ~line 411) or a first-lane success toast pointing at Credentials and the coordination sidebar.
   Since onboarding (finding P1) is unreachable after first run, these are the product's two
   named differentiators and currently have no in-product discovery path for the common "already
   has a CLI" user. Medium effort, very high impact on differentiator visibility.
4. **Add a link back to onboarding / "connect another provider" from Credentials.** One button on
   `app/src/pages/credentials.ts` that navigates to `{name: 'onboarding'}`. Trivial effort, fixes
   a genuinely orphaned, well-built screen.
5. **Give the lane grid a real answer for >6 lanes** beyond 3-column truncation. Options: a
   compact "list" density (one line per idle lane, expand on demand) as a fourth layout mode next
   to grid/rows/focus in `workspace.ts`'s `layoutControl`, or auto-recommend `rows`/`focus` once
   `order.length` crosses a threshold. Medium effort, directly protects the product's core
   "parallel lanes" promise at the scale it explicitly supports (up to 10/provider).
6. **Close the gap between AGENTS.md's Preview/Design vision and the shipped 97/184-line pages**,
   or scope down the marketing language to match what's built. Either build toward DOM/console/
   network inspection inside `preview.ts`, or (cheaper, immediate) adjust AGENTS.md's designed-
   screens description so the product doesn't over-promise relative to what a new user finds.
7. **Skip the splash "press enter" gate for returning users with an active workspace.** In
   `app/src/pages/splash.ts`, when `canStart` is already true and this isn't a first run,
   auto-advance after the daemon ping resolves rather than requiring a keypress. Low effort,
   removes friction on every single app open.
8. **Add column headers to the Usage "provider usage" table** (`app/src/pages/usage.ts`) —
   trivial CSS/markup change, removes an unnecessary "what am I looking at" moment.
9. **Give the empty state a "recent workspaces" affordance**, not just a raw directory input. Users
   restarting the app or switching machines currently retype/re-browse a path every time unless a
   project already has live sessions (which populates the rail's project list). Medium effort,
   meaningful daily-use improvement.
10. **Visible scroll affordance in the rail's nav groups at short viewports** (`app/styles.css`
    `.rail-scroll`) — a bottom fade/shadow when content overflows. Low effort, low-but-real
    polish for laptop-screen users.

## 4. Already good — do not break

- The **command palette and keyboard shortcuts system** (`app/src/shell.ts`): fuzzy search across
  navigation, running lanes, and contextual page commands, all in one dialog, fully documented in
  a matching shortcuts sheet. This is genuinely best-in-class.
- **One shared launch form** (`app/src/launch.ts`) powering the empty state, the `+ agents` sheet,
  and the New Session page — do not fork this into three implementations.
- **The credential chain UI** (`app/src/pages/credentials.ts`): numbered fallback order, explicit
  "not connected" states with the exact fix command, manual-only accounts kept separate from
  auto-fallback. This is the clearest expression of the product's actual differentiator in the
  whole app.
- **The coordination sidebar's data density** (`coordination-panel.ts`, visible in every workspace
  screenshot): tasks/files/handoffs/messages/memory/checks in one glanceable column, with a
  separate setup tab for master brief/planner/skill/evals. Keep this dense — do not "simplify" it
  into fewer visible fields.
- **Main-agent-first lane ordering** and the lead/subagent visual hierarchy in the grid
  (`workspace.ts:37-52`, the "main · 2/10 subagents" pill) — correctly encodes the orchestration
  model in the layout itself rather than requiring a legend.
- **Rail collapse-to-icons with live lane awareness** (attention dots, lead/subagent markers) —
  useful ambient status that most competitors in this category don't have.
- **Never wrapping the real CLI** — confirmed throughout (onboarding buttons call
  `api.createSession` and land the user directly in a live terminal running the actual provider
  CLI's own login flow). This is the architectural promise in `CLAUDE.md`'s "one rule" and it
  holds up in every flow I traced.
